# v1.2 — GKE Adapter

**Goal:** Bring the full kua lifecycle to Google Kubernetes Engine, **Standard** clusters first. For **Autopilot**, kua runs as readiness + verification + coordination only, because Google manages the nodes.

**GKE concepts to map (verify each against current Google Cloud docs before coding)**
| kua concept | GKE equivalent |
|---|---|
| Control plane version | `cluster.currentMasterVersion` |
| Available versions | `getServerConfig` per location & release channel (validMasterVersions, channels) |
| Node group | Node pool (`version`, `config.imageType`) |
| Upgrade insights | Recommender deprecation insights for GKE clusters (verify insight type), plus GKE's automatic upgrade pausing when deprecated API usage is detected (verify) |
| Surge / blue-green | Native node pool `upgradeSettings.strategy` = SURGE or BLUE_GREEN (with batch soak, node pool soak) |
| Maintenance | Maintenance windows & exclusions |
| Auto-upgrade | Release channels (Rapid/Regular/Stable/Extended) — auto-upgrade is effectively mandatory on channels |

**Key design decision for GKE:** GKE already has native blue/green node pool upgrades with soak. kua should **drive and gate the native mechanism**, not reimplement it. It triggers the upgrade with a blue/green strategy, uses batch soak durations as verification windows, and completes or rolls back through the native API depending on verification results. Declare this via the capability `native_bluegreen`.

**Auto-upgrade coordination:** Clusters on release channels will be auto-upgraded by Google. kua uses **maintenance exclusions** (e.g. "no minor upgrades" scope, verify) to hold minor upgrades until the kua campaign is approved. It never disables channels silently; the exclusion change goes through a PR.

TASK V12-T09: GKE mutating ops.

- begin_control_plane_upgrade: ClusterManagerClient.update_master(name=projects/p/locations/l/clusters/c, master_version=<hop version>) → Operation; poll get_operation → DONE/errors.
- Node phase (native_bluegreen capability): ClusterManagerClient.update_node_pool with node_version=<hop> and upgrade_settings strategy BLUE_GREEN (standard_rollout_policy batch_node_count / batch_percentage, batch_soak_duration, node_pool_soak_duration from plan: soak) — verify field names.
  * During soak phases, kua runs verification (core verify) on a schedule.
  * On pass → call complete_node_pool_upgrade to finish early OR let soak elapse (settings).
  * On fail → rollback_node_pool_upgrade (native) and raise a gate.
  * PDB behaviour: GKE respects PDBs during drain up to a timeout — detect stuck drains via operation progress/metrics + Kubernetes events, and gate (never let it silently force).
- Surge strategy supported as alternative (settings), with per-batch verification via operation progress.
- Core cordon/drain actions are not used for native_bluegreen pools (planner selects actions by capability).
- IAM: custom role with container.clusters.update, container.operations.get, etc. (derive from calls) in infra/gcp/iam/.
- Tests with mocked operations.
