# v0.4 — Control Plane, Managed Add-ons, Multi-hop & Other Compute Types

**Goal:** Complete the EKS upgrade lifecycle. The agent executes the **one-way control plane upgrade** behind the strictest gate, upgrades **EKS managed add-ons**, orchestrates **multi-hop** campaigns (e.g. 1.29 → 1.32), and handles **Karpenter, Fargate, and self-managed** node groups.

**The gate rules get stricter here**
- Tier-2 (control plane) needs 2 approvers, neither the PR author, plus a fresh drift check at execution time.
- Pre-CP remediation (Tier-1) must be verified as *live* in the cluster, not just merged.
- A pre-upgrade backup must succeed before the control plane moves.
- The executor gets `eks:UpdateClusterVersion` only in this version, scoped to declared clusters.

**Definition of done**
- Full single-hop flow: Tier 1 → 2 (CP + add-ons) → 3 → 4, executed end to end on the sandbox.
- Multi-hop plan executes hop by hop with a gate per hop and skew tracking.
- Karpenter, Fargate, and self-managed paths work or produce precise manual runbooks.

## V04-T03 — Action: control plane upgrade

**Why:** Requirement #4 — one version jump at a time; the only irreversible step in the whole system.

**Antigravity prompt:**
```
Read docs/plan/00-project-context.md (section 2 hard facts 1–2) and follow them. Implement only this task.

TASK V04-T03: Implement action control_plane_upgrade (kua/executor/actions/controlplane.py).

- Preconditions: precp_gate done for this hop in this execution; backup done; current CP version == hop - 1 (exactly one minor below); no in-progress cluster updates (eks.list_updates + describe_update status InProgress → wait); cluster status ACTIVE; all node groups' kubelets within skew after this hop (versions.max_skew_after_hop ≤ 3) — else fail (plan bug).
- Mode A (IaC-owned cluster version): the agent does NOT call UpdateClusterVersion. is_already_done checks CP version == hop; while not, returns waiting with message "waiting for your pipeline to apply the Tier-2 PR" (poll every 60s, timeout configurable, e.g. 6h). Document that the executor still provides gating, backup, and verification around the user's apply.
- Mode B: eks.update_cluster_version(name, version=hop, clientRequestToken=idempotency key). Store update id. Return in_progress; subsequent invocations describe_update → Successful → done; Failed/Cancelled → failed with errors (post details to PR). A failed CP update usually leaves the CP on the old version — confirm via describe_cluster and say so explicitly in the comment.
- Audit with the highest detail: before/after versions, update id, approvers list copied from gate.
- Executor IAM: add eks:UpdateClusterVersion + eks:DescribeUpdate + eks:ListUpdates scoped to var.cluster_arns in the Terraform module (remove the explicit Deny added in v0.3 for this action only).
Tests with Stubber (success, failed update, precondition failures, Mode A waiting).
```

## V04-T07 — Multi-hop planner v2

**Antigravity prompt:**
```
Read docs/plan/00-project-context.md (section 2 hard fact 2) and follow it. Implement only this task.

TASK V04-T07: Improve kua/plan/generate.py for multi-hop campaigns.

- Input options: settings.plan.node_strategy = "final_hop_only" | "every_hop" | "skew_minimal" (default skew_minimal).
  * final_hop_only: node blue/green only after last CP hop — rejected if skew would exceed 3 at any point.
  * every_hop: blue/green after every CP hop (safest, most churn).
  * skew_minimal: compute the minimal set of hops after which nodes must move so kubelet skew never exceeds settings.plan.max_skew (default 2 — leave headroom below the hard limit of 3; document why).
- Deprecated API removals: Tier-1 remediation steps are attached to the earliest hop whose removal requires them, but all Tier-1 steps must be satisfied before the first CP hop if they are compatible with the current version (prefer early remediation).
- Add-on compatibility per hop: compute a version chain per add-on (a sequence of versions each compatible with consecutive hops) using the matrix; if none exists, emit a planning error with details.
- Plan gets campaign metadata: campaign_id, hops with per-hop gate references; each hop's tier-2 is a separate PR.
- Expiry per hop: later hops re-validate drift at start; plan expiry for campaigns = settings.plan.campaign_ttl (default 14 days).
Tests: 1.28→1.32 with nodes at 1.28 under each strategy; add-on chain resolution; unsatisfiable chain error.
```
