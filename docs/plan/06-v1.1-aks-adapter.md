# v1.1 — AKS Adapter

**Goal:** Everything that works for EKS (scan → plan → PR gates → execute → verify → audit) works for Azure Kubernetes Service, through the provider interfaces refactored in v1.0-T04. The reasoner stays on Amazon Bedrock; only the provider layer changes.

**AKS concepts to map (verify each against current Microsoft docs before coding)**
| kua concept | AKS equivalent |
|---|---|
| Control plane version | `managedCluster.kubernetesVersion` / `currentKubernetesVersion` |
| Available upgrades | Managed Clusters "get upgrade profile" (`az aks get-upgrades`) |
| Node group | Agent pool (System / User mode) |
| Node image | Node image version (separate from Kubernetes version) |
| Managed add-ons | AKS add-ons & extensions (e.g. monitoring, Azure Policy, KEDA, Istio-based service mesh add-on) |
| Upgrade insights | AKS stops upgrades when it detects usage of deprecated APIs removed in the target (verify feature name/behaviour) + Azure Advisor recommendations |
| Surge | Agent pool `upgradeSettings.maxSurge` (and drain timeout / node soak settings — verify) |
| Maintenance window | Planned maintenance configurations (`aksManagedAutoUpgradeSchedule`, `aksManagedNodeOSUpgradeSchedule`) |
| Auto-upgrade | Auto-upgrade channels (none/patch/stable/rapid/node-image) |

**Special AKS rules**
- The system node pool must always keep capacity for system pods. Blue/green for a system pool needs a new *System-mode* pool before the old one is drained.
- Control-plane-only upgrade is supported, then agent pools separately. Enforce skew rules as AKS documents them.
- Auto-upgrade channels can race with kua. Detect them and require them to be `none`, or coordinate with maintenance windows (planner blocker otherwise).
