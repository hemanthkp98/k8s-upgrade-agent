# v1.3 — On-Prem Adapter (kubeadm & RKE2)

**Goal:** Extend kua to self-managed clusters, where **you own the control plane, etcd, and the node OS**. This is the most differentiated target, and also the most dangerous, because nothing is managed for you.

**What changes versus cloud providers**
| Concern | Cloud (EKS/AKS/GKE) | On-prem |
|---|---|---|
| Control plane upgrade | One API call | Per-node procedure on each control plane node, in order |
| etcd | Managed, invisible | You back it up (snapshot) and verify it before anything else |
| Node "blue/green" | Create a new pool | Usually in-place: cordon → drain → upgrade packages → restart kubelet → uncordon (blue/green only if you have spare hardware/VMs) |
| Transport | Cloud APIs | Remote execution on hosts: SSH, or **AWS Systems Manager hybrid activations** (fits the AWS-centred design) |
| Packages | Managed | kubeadm/kubelet/kubectl packages; `pkgs.k8s.io` repos are **per minor version** and must be switched each hop |
| Rollback | Nodes only | Nodes: package downgrade possible for kubelet; control plane: restore from etcd snapshot (disaster recovery, not rollback) |

**Design decisions**
- **Host actions are allow-listed "host playbooks"**, never free-form shell. Each is a versioned, reviewed script with typed parameters, checksum-pinned, and executed through a transport interface.
- **Transport options:** `ssm` (default: AWS SSM Run Command via hybrid activations, audited by CloudTrail + kua audit) or `ssh` (asyncssh, host keys pinned, dedicated user with sudo limited to the playbook runner).
- **Air-gapped / no-LLM mode** is a first-class option. The reasoner is optional; every decision point also works with deterministic rules plus human gates.
- **In-place upgrades are the default for nodes**; blue/green is optional when a VM pool provider exists (vSphere/Proxmox/OpenStack integrations are out of scope for v1.3 and noted as future).

## V13-T02 — Transport & allow-listed host playbooks

**Why:** The on-prem equivalent of principle 1. Arbitrary shell on control plane nodes is the biggest risk in the whole project.

**Antigravity prompt:**
```
Read docs/plan/00-project-context.md (principles 1, 6, 9) and follow them. Implement only this task.

TASK V13-T02: Implement kua/providers/onprem/transport/ and playbooks/.

1. Playbooks: kua/providers/onprem/playbooks/<name>/<version>/run.sh + manifest.yaml {name, version, description, params: {name: {type: str|int|enum, pattern, enum}}, mutating: bool, timeout_seconds, requires_root}. Scripts are POSIX sh/bash with `set -euo pipefail`, take params ONLY via environment variables validated at the top of the script (regex), print a final JSON line `KUA_RESULT {...}` for structured output. SHA-256 of each script recorded in a generated playbooks.lock file; runtime verifies the hash before sending.
   Initial read-only playbooks: host_facts, etcd_health, kubeadm_upgrade_plan, cert_expiry, package_versions, disk_space.
2. Transport interface: run_playbook(host, name, version, params) -> PlaybookResult(exit_code, stdout_tail (sanitized, max 20KB), result_json, duration).
   - SsmTransport: ssm.send_command with document AWS-RunShellScript; commands = a fixed wrapper that writes the script content (base64) to a temp file, verifies sha256, runs with env params, deletes the file. Instance ids from host map (hybrid activation mi-*). Poll get_command_invocation. Output also to S3 (optional). Tag commands with kua execution id.
   - SshTransport: asyncssh with known_hosts pinning (no auto-accept), key from Secrets Manager, runs `sudo -n /usr/local/sbin/kua-runner <name> <version>` where kua-runner is an installed wrapper that only executes playbooks from a local, root-owned, hash-verified directory (ship installer playbook + docs). Stream-free: capture output only.
3. Param validation happens twice (Python before sending; script on host).
4. Every invocation audited (host, playbook, version, params redacted, hash, exit code, duration).
5. Tests: param validation (injection attempts like "1.30; rm -rf /" rejected), hash mismatch refusal, SSM Stubber flows, SSH with asyncssh test server or mocks.
```

## V13-T06 — kubeadm control plane upgrade actions

**Antigravity prompt:**
```
Read docs/plan/00-project-context.md (section 2) and follow it. Implement only this task.

TASK V13-T06: Implement mutating playbooks + actions for kubeadm control plane (follow the official "Upgrading kubeadm clusters" procedure for the target version — read it first and cite it).

Playbooks (mutating, one bounded step each):
- pkg_repo_switch(minor): point the Kubernetes package repo to the target minor (apt source list / yum repo file), refresh metadata.
- pkg_install(package, version): unhold → install exact version → hold. Allowed packages enum: kubeadm, kubelet, kubectl.
- kubeadm_upgrade_apply(version): `kubeadm upgrade apply v<version> --yes` on the FIRST control plane node only (with --etcd-upgrade per config; default true — verify flag).
- kubeadm_upgrade_node(): `kubeadm upgrade node` on other control plane nodes and workers.
- kubelet_restart(): systemctl daemon-reload && systemctl restart kubelet; then wait for node Ready (done by Python via k8s API, not in script).
Actions (executor): per CP node, strictly sequential:
 1. Verify etcd healthy + snapshot exists for this execution.
 2. cordon + drain the CP node (core drain, which skips static pods / DaemonSets).
 3. pkg_repo_switch → pkg_install kubeadm.
 4. first node: kubeadm_upgrade_apply; others: kubeadm_upgrade_node.
 5. pkg_install kubelet + kubectl → kubelet_restart → wait Ready + API /readyz on that node's apiserver → etcd_health.
 6. uncordon.
 7. Post-node verification; gate before moving to the next CP node (configurable auto-continue if all checks pass).
Failures stop the sequence; runbook generated (T10). Never proceed to the next CP node if etcd health or quorum is degraded.
Tests with fake transport scripting results.
```

## V13-T09 — On-prem planner specifics

**Antigravity prompt:**
```
Read docs/plan/00-project-context.md and follow its principles. Implement only this task.

TASK V13-T09: Planner for on-prem.
- New step types: EtcdSnapshot, CpNodeUpgrade(node, order, first: bool), WorkerBatchUpgrade(nodes), PackageRepoSwitch (implicit per node), Rke2PlanApply.
- Ordering per hop: Tier-1 remediation → etcd snapshot → CP nodes sequential (Tier-2, 2 approvers) → workers batches (Tier-3) → verification. Multi-hop repeats including repo switch per hop.
- HA constraints: never upgrade more than 1 CP node at a time; with 3 etcd members, block if any member unhealthy; with 2 members (even) require explicit acknowledgment.
- Capacity: batch size limited so remaining schedulable capacity (allocatable CPU/mem of uncordoned nodes) ≥ current requests × (1 + headroom 20%) — compute from Node allocatable and pod requests; ONPREM-CAP-BATCH finding if even batch size 1 fails.
- Tests.
```
