# v0.3 — Execution Engine on AWS + Node Blue/Green

**Goal:** When a Tier-3 PR (green node group) is merged, the agent executes the node phase safely:
create green (tainted) → canary → untaint green → cordon blue → drain in PDB-aware batches with SLO checks → soak → open the Tier-4 removal PR.

Control plane execution is **not** in v0.3 (that's v0.4). v0.3 is useful on its own for clusters whose nodes lag behind the control plane, which is very common.

**Architecture introduced in v0.3**

```
GitHub (merge of tier PR)
   │  workflow_run / push on protected branch
   ▼
GitHub Actions ──OIDC──▶ IAM role kua-trigger (states:StartExecution only)
   ▼
Step Functions "kua-upgrade" (Standard)
   ├─ Lambda kua-step (container image; runs executor actions)
   ├─ DynamoDB kua-state (execution state + per-cluster lock)
   ├─ AgentCore Runtime "kua-reasoner" (Bedrock; verification judgement + summaries)
   ├─ CloudWatch Logs (audit, hash-chained)
   └─ GitHub App (comments, check runs, mid-run gate)
```

**Why Step Functions + Lambda, not "the agent does it":** drains take a long time, need retries, waits, and human gates. Step Functions gives durable waits (up to a year), retries, and a visual execution history. The LLM is consulted at decision points only.

**Definition of done**
- Terraform module deploys the whole execution stack in one `terraform apply`.
- Merge-triggered execution with plan signature + drift re-check.
- Node blue/green works on managed node groups, with canary, batched drain, per-batch verification, mid-run approval, soak, and rollback.
- End-to-end test on a sandbox EKS cluster.

## V03-T02 — Action framework

**Why:** Principle 1 — every mutation is a named, allow-listed, idempotent action. The LLM can never introduce a new action.

**Antigravity prompt:**
```

TASK V03-T02: Implement kua/executor/actions/base.py and registry.

- class ActionContext: execution_id, plan, step, provider, k8s client, state store, audit logger, settings, dry_run: bool.
- class ActionResult: status: Literal["done","in_progress","waiting","failed"], output: dict, retry_after_seconds: int | None, message.
- class Action(ABC):
    name: ClassVar[str]
    mutating: ClassVar[bool]
    def idempotency_key(ctx) -> str   # deterministic from plan_id + step id + action name + relevant params
    def preconditions(ctx) -> list[str]   # returns unmet precondition messages
    def is_already_done(ctx) -> bool      # checks live state
    def run(ctx) -> ActionResult          # performs ONE bounded unit of work (<10 min)

- execute_action(name, ctx): lookup (unknown → failed), lock renew, preconditions → failed with messages, is_already_done → done (audited as "skipped: already done"), dry_run → audit ACTION_PLANNED and return done, else audit ACTION_STARTED → run → ACTION_FINISHED/FAILED; persist via state store.
- Map plan step types to ordered action lists in kua/executor/stepmap.py, e.g. nodegroup_bluegreen → [create_green_nodegroup, wait_nodegroup_active, canary_smoke, untaint_green, cordon_blue, drain_blue (looped), soak, open_removal_pr].
```

```
6. Notify at start/end (Lambda "notify").
```

## V03-T10 — Batched drain with Eviction API & deadlock detection

**Why:** Requirement #5. The hardest operational step; must never force-delete and must detect PDB deadlocks rather than spin forever.

**Antigravity prompt:**
```
Read docs/plan/00-project-context.md and follow its principles. Implement only this task.

TASK V03-T10: Implement action drain_blue (kua/executor/actions/drain.py). Each invocation performs ONE batch step and returns in_progress until all blue nodes are drained.

Algorithm per invocation:
1. Load drain state from state store (nodes pending, current batch, per-pod eviction attempts, first_429_at per pod).
2. If no current batch: pick next `drain_batch_size` blue nodes (order: fewest pods first, then spread across AZs). Record batch.
3. For each node in batch, list pods (fieldSelector spec.nodeName). Skip: DaemonSet-owned pods, mirror/static pods (annotation kubernetes.io/config.mirror), pods already terminating, pods in Succeeded/Failed phase. Pods without controllers: evict ONLY if the plan acknowledged DRAIN-NO-CONTROLLER, else return waiting (human gate) with list.
4. For each remaining pod: create policy/v1 Eviction. Responses:
   - 201 → record.
   - 429 (PDB) → record first_429_at; do not retry faster than every 10s (return in_progress with retry_after 15).
   - 404 → gone, fine.
   - 500 with "multiple PDBs" → failed-for-pod: waiting gate listing pod & PDBs.
5. Deadlock detection: if any pod has been blocked by 429 for longer than settings.drain.pdb_block_timeout (default 15 min) → call the reasoner (T12) with sanitized facts (PDB status, matched workload replicas/ready, pending pods and their events) to produce an explanation, then return waiting (human approval gate) with options surfaced in the PR comment: "scale up <workload> by 1 temporarily", "wait longer", "abort & rollback". The agent NEVER edits PDBs or force-deletes on its own. If a human picks "scale up", execute the allow-listed action scale_workload(+1) and record original replicas for restore after drain.
6. A node is drained when only skippable pods remain. When the whole batch is drained → run verification (T11) for this batch → if pass, pause drain_batch_pause_seconds then next batch; if fail → failed (triggers rollback).
7. Respect terminationGracePeriodSeconds: wait for evicted pods to disappear, up to max(grace)+60s, before calling the node drained.
8. Also watch for replacement pods stuck Pending > 5 min (check events for FailedScheduling / volume node affinity conflict) → waiting gate with explanation (common: zonal EBS without green capacity in that AZ).
Tests: fake API simulating 201/429/404 sequences, deadlock timeout path, Pending detection, DaemonSet skip, idempotent resume mid-batch.
```
